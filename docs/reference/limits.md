# Limits

This page lists the limits Agent Kourier places that an operator, a Binding author or an agent backend can run into. Each row gives the value,
where it applies, what happens past it, and whether a setting changes it. The reasons and the how-tos are on the pages the rows link to.

Where a value is a constant of the code, or a default the code fills in, a test compares it with this page in every test run. Some values are
rules of Kubernetes or of a chat platform that the code does not hold as a constant, and a few are shapes of the code, such as the message
fields a trigger reads; the tests read what the code does for those. The figures that were measured, and not read from the code, say so.

The page lists the limits you can run into. It leaves out numbers that change nothing an operator, a Binding author or an agent can see: the
intervals and batch sizes of the background loops, the retry pacing of the press worker and the outbox sweep, and Slack layout numbers that a
lower cut earlier in the broker hides.

**What "past it" means.**

- **Refused at load**: the broker's own validation rejects the object when it reads it. On the files route one such object fails the whole
  config: at start the broker exits with code 2, and on a reload it keeps the last good config. On the custom resource route a new object is
  not served, and an object that was good before keeps being served as its last good generation. See [What a bad object does](../explanation/config-routes.md#what-a-bad-object-does).
- **Refused by the API server**: the CRD schema rejects the create or update, so the object never reaches the broker. This is the custom
  resource route only. A schema bound that the code also holds is refused at load too, because the broker checks every object it reads.
  The schema counts characters and the broker counts bytes, so a value of multibyte characters can pass the API server and still be refused at load.
- **Cut**: shortened. Where the text is shown to people, the end is marked `… (truncated)`<!--limit:truncatedMark-->.
- **Ends the turn**, **dropped**, **queued**: the turn stops, the item is thrown away, or it waits. The row says which, and what the thread is told.

| Replicas that do the work | One | With SQLite, `replicaCount` above 1 fails while the chart renders. With Postgres the replicas elect a leader through a Lease: one works and the others stand by. See [Run two replicas](../how-to/high-availability.md). | `store.type`, `replicaCount` |
| ChatConnections one broker serves | `16`<!--limit:servedConnections--> in all. The broker's own (`AGENTKOURIER_CHAT_CONNECTION`), if it has one, takes the first place, and with custom resources the ChatConnections of the namespaces it admits take the rest by age: `creationTimestamp`, oldest first, then namespace, then name. It admits the namespaces in `AGENTKOURIER_CONNECTION_NAMESPACES` and those whose labels match `AGENTKOURIER_CONNECTION_NAMESPACE_SELECTOR`, or every namespace when none of the three variables is set or the selector is `{}`: then the 16 places are shared by every ChatConnection of the cluster. With no own connection all 16 places go by age. | With files, a directory that holds none or several stops the start (exit code 2). With custom resources the broker serves its own connection, if it has one, and the oldest ChatConnections of the namespaces it admits, up to the 16, and no others. A connection past the sixteenth is not run, and the Bindings it admits (those of its own namespace and of the namespaces in its `allowedNamespaces`) say `ConnectionNotServed`, with the reason that the broker serves at most 16, and the leader counts them in `agentkourier_config_binding_rejections{reason="ConnectionNotServed"}` ([Metrics](metrics.md)). The source logs it once at WARN, and it is served again, logged once at INFO, when a connection ahead of it is deleted or its namespace stops being admitted. An invalid connection takes a place too, and so does one whose Secret the broker cannot read; a deleted one keeps its place until its deletion takes effect, and so does a second connection of a Slack or Microsoft Teams app that is not run (the next row), so the choice depends on the objects' ages and names and not on their contents. | How soon a team ChatConnection's runtime follows a change | The broker looks at the team connections it serves each `5s`<!--limit:superviseEvery-->. It reads the connections from the config snapshot, so a ChatConnection added, edited or no longer served is seen after the config reload that carries it, and the credentials from the Secret informers' cache, so a changed Secret is seen at the first look after the cache has it. A connection is started, restarted (when its generation or the content of its Secret changed) or stopped at that look. | Until then the runtime is as it was. A Secret that cannot be read when the connection is first seen is looked at again at each look, and the connection starts once it can be read. A Secret that does not exist yet is read at the first look after it is created. One that the API server denied (the team's Role is missing) is asked for again only at the config recheck, so a Role applied late is noticed after up to about 1 m 10 s (the row on a Secret the API server answers forbidden, below, has the figures; no setting changes them) and then at the next look. | None |
| Asking Slack whose bot a team connection's token is | Each connection is asked once, with `auth.test` and then `bots.info` for the bot it names, before it starts, and again only if its ChatConnection or Secret changes. The own connection, if there is one, is asked the same when the broker serves a team connection. Each call is cut at `10s`<!--limit:identifyTimeout-->. | The connection does not start, and is asked again at the next look, unless Slack answered that the token is refused (`invalid_auth`, `token_revoked`, `token_expired`, `account_inactive`, `not_authed`): then it is not asked again until its ChatConnection or Secret changes. A connection whose Slack app (the app ID `bots.info` gives, so one app installed in two workspaces counts once) another served connection uses is not run: the older is served, a younger one that runs is stopped when an older of its app turns up, and the Bindings of the one not run say `ConnectionNotServed`. | None |
| Waiting for a team connection's Slack run to stop | When the broker stops a team connection (removed, or restarted on a change) it waits at most `5s`<!--limit:runtimeStopTimeout--> for the run to return. | A WARN says so and the broker goes on: the run has been told to stop and ends on its own. | None |
| Reconnecting Slack after the connection is lost | A connection that cannot be opened, or that was lost and cannot be opened again, ends the run of the connection, and the broker runs it again after a wait. The first wait is `1s`<!--limit:reconnectBase-->, and each wait after a failure is twice the one before, up to `60s`<!--limit:reconnectMax-->. Each wait is cut at random by up to half of itself, so it is never shorter than half of that pause or longer than it, and each connection draws its own: connections that fail together do not retry together. The pauses start again from `1s` after a run that lasted `120s`<!--limit:reconnectReset--> or more before it failed. When Slack answers a call with a rate limit and a Retry-After longer than the wait, the broker waits that long, but no longer than `5m`<!--limit:retryAfterMax-->. | The broker retries for as long as Slack does not reject the credentials, so the longest wait is `60s`, or Slack's Retry-After when that is longer. A Retry-After past `5m` is cut to `5m`. A rejection of the tokens (`invalid_auth`, `not_authed`, `token_revoked`, `token_expired` or `account_inactive`) is not retried: the own connection, if there is one, exits the process with code 1, and a team connection stops (`ChatCredentialsRejected`); a broker with no own connection never exits for it. `agentkourier_chat_connected` is 0 from when the connection is lost, which is when the library starts to connect again, until Slack's hello. A WARN, `slack connection ended; connecting again`, says why and how long the wait is. | None |
| What the Slack client library does itself on a connection | slack-go v0.36.0, read in its source. It connects again at once, with no wait and no jitter, when Slack asks for a refresh (a `disconnect` message) and for the first attempt after the connection is lost. It drops a connection on which Slack has sent no WebSocket ping for more than `30s`, which it checks every 30 seconds, so a silent connection is dropped 30 to 60 seconds after the last ping, and counts the WebSocket handshake as failed after `45s`. The call that opens the connection (`apps.connections.open`) has no timeout of its own: the broker bounds it with its HTTP client (the next row). | A failed attempt ends the run, and the row above sets the wait. The library's own retry, which started at 100 ms, doubled up to 5 minutes and had no jitter, no longer runs: it is not used for any attempt, the first connection of a run included. | None |
| One Slack Web API call | `30s`<!--limit:slackAPITimeout--> for each call, counted from the start of the request to the end of the response body: the dial, the TLS handshake, the wait for the answer and the reading of it. The bound is on the broker's HTTP client for the Slack Web API, so it applies to every call the Slack adapter makes, the `auth.test` that each run starts with and the `apps.connections.open` that opens each Socket Mode connection and each reconnection included. It does not apply to the Socket Mode WebSocket, which the client library dials with its own dialer (the row above), so a connection that stays up is not cut. A call that the adapter bounds more closely, such as `users.info` (`5s`) or the membership checks of a button press (`10s` in the broker), ends at its own bound. | The call fails with a client timeout error. The adapter classes that as a transient failure, which is not a rejection of the credentials, so nothing is stopped for it. When it is `auth.test` or `apps.connections.open`, the run of the connection ends with the failure, and the row on reconnecting sets the wait before the broker runs it again. Without the bound a call on a connection that a network blip had left dead held the run for up to two minutes (53 and 118 seconds were seen) before it failed. | None |
| A request to the chat listener (`AGENTKOURIER_CHAT_LISTEN`; there is none while it is unset) | A body of up to `1 MiB`<!--limit:chatBody-->, and a request line and headers of up to `16 KiB`<!--limit:chatHeaders-->. The headers must arrive within `1s`<!--limit:chatReadHeader--> and the whole request within `2s`<!--limit:chatRead-->, both counted from the start of the request. The connection's handler is given a context that ends `3s`<!--limit:chatHandler--> after the body was read, and the answer must be written within `6s`<!--limit:chatWrite--> of the end of the headers: the time to read the request, the handler's 3s, and `1s`<!--limit:chatAnswer--> to write the answer. A Microsoft Teams connection's handler asks for a longer deadline, for every request of the connection (the row on the answer to a press of a Microsoft Teams card): its context ends then instead, and its answer must be written within the same 1s after it. A kept-alive connection is closed after `30s`<!--limit:chatIdle--> with no request. | A body past its cap is answered 413 and the connection's handler is not called: a body with a declared length is not read, and one sent in chunks is read only to the cap. Headers past theirs are answered 431, by Go's HTTP server, which allows a few KiB over the cap. A request whose headers are late is cut, its connection closed, and one whose body is late is answered 400; neither reaches the handler. Past its context the handler is expected to answer, and an answer not written within its bound is cut with the connection. Slack waits about 3 seconds for an answer before it sends a request again (Slack's own behaviour, not checked here), so these bounds hold a request only as long as its answer can still count. A POST to a connection with no route on this replica (a standby, a leader whose connection is starting, restarting or down, a connection that takes nothing over HTTP, or none of that name) is answered 503 with a `Retry-After` of `5s`<!--limit:chatRetryAfter-->, and the connection closed, before any of its body is read; it is counted as `no_route` on `agentkourier_chat_listener_requests_total`. | None |
| Requests the chat listener hands to their handlers at once | `32`<!--limit:chatInFlight--> requests whose connection's handler is running, across all connections. A request takes a place only once its body has been read whole, so a client that sends its body slowly holds none. A press of a Microsoft Teams card holds its place while it waits for its decision (the row on the answer to a press of a Microsoft Teams card), and at most `16`<!--limit:pressWaitsMax--> presses wait so at once: a press past them is recorded and answered at once as received, as if it had not been decided in the wait. | While every place is taken, the next request is answered 503 with a `Retry-After` of `5s`<!--limit:chatRetryAfter-->, and the connection closed, before any of its body is read; a request whose body was read while the last places were taken is answered 503 with the same `Retry-After` once it has been read. Both are counted as `busy` on `agentkourier_chat_listener_requests_total`. Slack sends them again; Microsoft Teams sent a message activity answered 503 at once again once, about 0.6 seconds later, when measured (the row on a request that Microsoft Teams sends). | None |
| Request bodies the chat listener holds at once | `32 MiB`<!--limit:chatBodyBudget--> of live body buffers, across all requests being read or handled, from the start of the read until the handler returns: an eighth of the chart's default memory limit. A body is read into buffers of `4 KiB`<!--limit:chatBodyChunk-->, each counted before it is allocated, so a request being read holds at most 4 KiB more than it has received (a body of the full 1 MiB holds 1 MiB and 4 KiB). A request holds its first 4 KiB as soon as its headers are read, whatever it has sent of its body, so the budget is held either by 8192 connections that are in the middle of their bodies, until the bound on reading the request cuts them, or by 32 MiB actually sent. The number of connections is not counted in it. | A request whose next buffer does not fit is answered 503 with a `Retry-After` of `5s`<!--limit:chatRetryAfter-->, and the connection closed, without the rest of its body being read; it is counted as `busy`. Slack sends it again; Microsoft Teams sent a message activity answered 503 at once again once, about 0.6 seconds later, when measured (the row on a request that Microsoft Teams sends). | None |
| A request that Slack sends to a ChatConnection in HTTP mode (`spec.slack.mode: http`) | Its timestamp (`X-Slack-Request-Timestamp`) must be within `5m`<!--limit:slackSignatureAge--> of the broker's clock, either way, and its signature (`X-Slack-Signature`) the one the connection's `signingSecret` makes of the timestamp and the body. An event or a press that passes goes on the lane of its channel (the row on the events the adapter holds, in [Start investigations](#start-investigations-triggers-rates-and-probes)), and the answer waits at most `2s`<!--limit:slackHTTPAckWait-->, counted from when the connection's handler was given the request, for the broker to take it. | A request outside the time window, or not signed with the secret, is answered 401, and nothing of its body is decoded. An event the broker has not taken within the wait is answered 503, and so is one that the lane's bounds shed or the broker could not take: Slack sends it again (Slack's own behaviour, not checked here). The broker may still take one that was answered 503 for the wait, and Slack's second copy of a message is then dropped as a duplicate once the first has been decided. Each answer is counted on `agentkourier_slack_http_requests_total` ([Metrics](metrics.md)). | None |
| A request that Microsoft Teams sends to a ChatConnection in `http` mode (`spec.teams.mode`), which the leader takes on its chat listener | The request's body is held to the chat listener's cap (the row on a request to the chat listener). Its bearer token must be signed RS256 by a key that the Bot Framework publishes and endorses for Microsoft Teams, name the connection's `spec.teams.appID` as its audience and the activity's `serviceUrl` as its service URL, and have an expiry and a not-before time within `5m`<!--limit:teamsTokenSkew--> of the broker's clock. A token waits at most `3s`<!--limit:teamsVerifyWait--> for the keys while they are being fetched, the chat listener's default deadline, although the connection's requests have a longer one (the row on the answer to a press of a Microsoft Teams card). The keys are fetched when the connection starts taking requests, their age is checked every `1h`<!--limit:teamsKeysCheck-->, and they are fetched again in the background once they are `12h`<!--limit:teamsKeysRefresh--> old, whether or not requests come, and used while that fetch fails until they are `24h`<!--limit:teamsKeysMaxAge--> old. A token whose key they do not hold makes one more fetch, and the next such token another only once that longest wait has passed. A published key of fewer than `2048`<!--limit:teamsMinKeyBits--> bits is ignored, as if it were not published. A fetch, the metadata and the key set together, is cut at `10s`<!--limit:teamsKeysFetch--> and reads at most `4 MiB`<!--limit:teamsKeysBody--> of each (the key set was about 0.8 MB in November 2026, measured). Accepted activities wait for the broker on a lane for each channel and are handed on in the order they came: a channel's lane holds `16`<!--limit:teamsChannelBacklog-->, and once the lanes hold `256`<!--limit:teamsPending--> in all, a channel that already has one waiting takes no other, while a channel with none still takes its first. A post that the broker does not take is given to it again on its lane, up to `4`<!--limit:teamsSinkAttempts--> times in all, after `1s`<!--limit:teamsSinkRetry--> and then twice as long after each further failure, up to `4s`<!--limit:teamsSinkRetryMax-->; the channel's later activities wait behind it. When the connection stops, what it accepted is handed on for at most `1s`<!--limit:teamsStopDrain--> more. | A token that fails a check is answered 401, and one that cannot be checked because no key set younger than a day could be fetched, or because its wait for a fetch ran out, 503; an activity with a longer ID, or a `:` where none may be, is answered 400, one of another tenant 403, and a request while the connection does not run (before it starts, or once it stops) 503. None of them is worked on. A refused token that the Bot Framework signed (one that names another app, is out of the skew, or fails the issuer, endorsement or service URL check) means the connection's app ID or the broker's clock is wrong, and is logged at WARN, one line for each reason every `10s`<!--limit:teamsRefusalLog--> with a count of those not logged; a log line quotes at most `256 bytes`<!--limit:teamsQuote--> of a value the request chose. An activity that comes again within the window is answered 200 and handed on to nothing; one remembered for less than the window because a generation filled early may be taken again. Any activity other than an invoke that its channel's lane cannot take is answered 503; an invoke is still answered, and only what it says of its channel is not recorded. A post still not taken after the last try is dropped, and the same activity is taken if it comes again. What is still waiting when the drain ends is dropped. What Microsoft Teams sends again was measured on a test tenant: an activity answered 200, or one whose request it held until it gave up (about 25 seconds for a message, 14 for an invoke), never; a message answered 503 at once, once, about 0.6 seconds later, with the same ID; an invoke answered 503, and other status codes, were not measured. So a message answered 503 is taken when it comes again if the lane has room by then, and lost if not, and an activity answered 200 and then dropped is lost. | None |
| The answer to a press of a Microsoft Teams card | The chat listener gives a Microsoft Teams connection's request a context that ends `8s`<!--limit:teamsInvokeDeadline--> after its body was read, in place of its 3s, and a press waits in it up to `6s`<!--limit:teamsPressWait--> for the worker that decides recorded presses to decide it. ## Build or connect an agent backend

### What the broker reads and holds

The backend of a Binding may be a tenant's, so the broker bounds each thing it reads. A bound is on one response or one event, never on a
stream's length. The values are constants of the binary: no chart value, file or custom resource field reaches them.
[The release that lowers the bounds](../how-to/upgrade.md#upgrade-to-the-release-that-lowers-the-bounds-on-what-it-reads) has what each means for an agent.

| Limit | Value | Past it | Setting |
|---|---|---|---|
| The agent card | `1 MiB`<!--limit:cardBytes--> | The card is not read, and no connection is made. A probe sets the Binding's `BackendReachable` condition to `False` with the reason `InvalidAgentCard`. The card is not an answer to a call, so what it does differs from the rows below: a **send** or a **lookup** that meets it is retried like any call that cannot reach the agent, and a send is given up after `15m` as an agent that cannot be reached; an **answer** to a paused task reopens the pause and tells the thread that the answer could not be delivered; a **follow** of a task, or the read of the task that comes before it, tells the thread, in a fixed sentence, that Agent Kourier could not connect because the agent's card is too large, and that once the card is fixed Agent Kourier must be restarted; it cancels nothing, and leaves the task recorded and running at the agent, followed by no one (the turn ends with the outcome `refused`); a **cancel** is not counted as done, and the record stays. Nothing follows that task again by itself: what releases it is a restart of Agent Kourier, which then reads the recorded task and follows it, and a restart interrupts every turn of every tenant on that broker while it runs. Read from the code and its tests. | None |
| One event of a stream, the lines of it up to the blank line | `2 MiB`<!--limit:eventBytes--> | The read fails at the bound, never as a shortened event. A reply that names no task has none to cancel: a send whose first event is too large, or a reply that is one message and no task. An answer to a paused task whose reply is too large before the agent names the task again ends the turn at once, with the same sentence, and Agent Kourier cancels the task that was answered, so that it does not stay paused for a person to answer into the same reply; the answer is not sent again. | What one turn holds of the agent's reply: its artifacts' text, tool results that wait for their call, and the bookkeeping of each tool part | `341 KiB`<!--limit:replyBytes--> | Ends the turn as an event does, however many events the reply came in. | `GetTask` that reads a task back: after a lost stream, a restart or a follow; to read a person's typed reply to a paused task, on the `a2a` dialect; and after an answer that the agent refused as busy or not ready, or whose outcome is unknown (the answer carries the task with its whole history) | `4 MiB`<!--limit:answerBytes--> | The answer is not read, and the turn ends with the outcome `response_too_large`, as for an event. | `GetTask` before a person's answer to a paused task that is pressed (a button, not a typed reply), which reads the task to tell what in the reply is new | `4 MiB`<!--limit:answerBytes--> | The read is dropped, and the answer is sent without it. | None |
| `CancelTask`. of many small objects at the bound costs much more than the same number of bytes of text. The figures are from a test process, not from a
pod: the Go test binary on a laptop, with the fake agent and the client in one process, and a pod's own baseline was not measured. With small
objects at the bound, two or three large responses read at the same time passed the chart's default limit of 256Mi. So the number of streams
or answers that fit is not a limit to plan by. An AgentBackend must be one you trust, or get a broker of its own, because the backend decides
how many large responses are in flight. The measurement and its counts are in
[the release that lowers the bounds](../how-to/upgrade.md#upgrade-to-the-release-that-lowers-the-bounds-on-what-it-reads).

## What has no limit

The broker does not bound these, and the code confirms it. Where the number can hurt, the row says what to do.

| What | What to do |
|---|---|
| Bindings, AgentBackends and ChatConnections in a cluster or a namespace, and the entries of `allowedNamespaces` | A cap of the schema or of `Validate` bounds one object, never how many there are. Put a `ResourceQuota` in each tenant's namespace with `count/bindings.agentkourier.dev` and `count/agentbackends.agentkourier.dev`. The API server then refuses a create past it with `exceeded quota` (measured on kind 1.37.0, as [Security](../explanation/security.md#what-the-people-who-write-these-objects-can-do) says; not run again for this page). In each admitted namespace (with every namespace admitted, in each namespace where someone may create one) add `count/chatconnections.agentkourier.dev` (the same Kubernetes quota for the kind, not run here): the broker serves at most 16 ChatConnections, the oldest first, so a team that makes many can leave a later team's out. Add `count/secrets` for the Secrets a Binding's token or an AgentBackend's header can name (Kubernetes's own object-count quota, not run here): it bounds how many Secrets exist, and not how many names the objects give the broker to follow, since it follows each name with an informer of its own whether or not the Secret exists. A quota limits the count and not the size. What the broker holds of the largest object that `Validate` accepts was measured in a test process, not a pod. The informer's cache holds about 0.17 MiB for an AgentBackend, 0.03 MiB for a ChatConnection and 1.75 MiB for a Binding, with the labels, annotations, owner references, finalizers and managed fields of an object not held at all. On top of that the broker keeps the object it decoded: 1.44 MiB for a Binding, 0.16 MiB for an AgentBackend, and the Snapshot serves the Binding's, so a Binding costs about 3.2 MiB, and 3.8 MiB when it is served (the trigger table is 0.63 MiB). Every broker owns, decodes and keeps the Bindings that name a ChatConnection that does not exist, and every AgentBackend of the cluster, whether or not a Binding names it, so these cost every broker whoever created them. A full `status` (16 conditions of 32768 bytes) adds 0.50 MiB to the informer's copy of a Binding, and the figures assume an empty one. The conditions and the rest of the figures are in [Security](../explanation/security.md#what-the-people-who-write-these-objects-can-do). |
| Streams and calls open to agents at once | Each has a size bound, but nothing bounds the number, so the bounds give the broker no total. Run only AgentBackends you trust, or give one its own broker, and size `resources.limits.memory` for the responses that can be in flight at once: see [what the broker reads and holds](#what-the-broker-reads-and-holds). |
| The length of a stream, and the text a stream carries in all | A stream runs as long as its turn. The broker holds only up to the reply bound, and a stream that sends text that is thrown away can run as long as its context. |
| Threads, sessions and turns at once | Each thread runs one turn at a time and queues the rest. Nothing bounds how many threads run turns at once, or how many replies queue in a thread. |
| A person's mentions | A `mention` trigger has no limit. A rate limit applies to bots only. |
| Secrets that the objects of a namespace name, denied or not | Each name that a served object refers to has an informer of its own, and the first request of each (two, for a name that is denied) is not paced: the client's limiter of 50 a second spreads them, so a thousand denied names take about 40 s to be asked once, and a read of another tenant's Secret that makes its own request waits behind them (inferred from how the limiter queues, not measured). After that a denied name costs at most the paced tries above, about 20 requests a second in all however many there are, and a name that does not exist or is allowed costs one open watch. Put a `count/secrets` quota and the quotas on Bindings and AgentBackends in each tenant's namespace, which bound the names (see [the security model](../explanation/security.md)). |
| The audit log and the votes | The audit log is kept for ever unless you set `auditRetention`. Nothing deletes a vote, and `auditRetention` does not reach them. |
| The upper bound of `rateLimit.maxRuns`, `maxConcurrent` and `maxRunsPerDay` | Only a lower bound is checked. |

## Add-ons

An [add-on](../explanation/add-ons.md) is a separate module with separate limits: no setting of the broker changes
them, and no limit above applies inside an add-on. The add-ons share a module, the kit, whose limits apply to every
add-on ([Every add-on](#every-add-on)); each add-on's section has the rest. The rows
give the add-on's environment variable, and the chart value that sets it, in which `<name>` is the add-on's block under
`addons`: `cma` or `ax`.

The values in code spans are constants or defaults of the kit's code or of an add-on's, and the tests of the module that
holds each compare it with this page.
